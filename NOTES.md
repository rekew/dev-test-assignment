# NOTES

## Задача 1. Распределение заказов по филиалам (task-1-dispatch)

### Что сделано
1. **Баг**: в `findNearest` координаты филиала были перепутаны (`b.lon, b.lat` → `b.lat, b.lon`), из-за чего заказ уходил не в ближайший филиал. Исправлено.
2. **Правила выбора**: добавлены `pickup_point` (пункт выдачи закреплён за филиалом), `city` (ровно один активный филиал магазина в городе заказа), `geo` с приоритетом филиалов города заказа (если их несколько — ближайший из них, иначе ближайший из всех). Порядок: `manual` → `single` → `pickup_point` → `city` → `geo` → `unassigned`.
3. **Дневной лимит**: филиал считается заполненным, если число уже принятых заказов за сутки (по Алматы, UTC+5, по `createdAt` заказа) >= `dailyLimit`. Если выбранный филиал заполнен — заказ уходит в ближайший незаполненный филиал магазина по правилу `geo` (с приоритетом города); если такого нет — `unassigned`. `manual` лимит не проверяет.
4. **API**:
   - `POST /orders/:id/assign` — 404 если заказа нет; повторный вызов возвращает ранее сохранённое распределение и не расходует лимит повторно (идемпотентность).
   - `GET /branches/:id/load?date=YYYY-MM-DD` — 400 без даты или при некорректной дате, 404 если филиала нет, иначе `{branchId, date, assigned, limit}`.
5. **Тесты**: закрыты все `test.todo`, добавлены unit-тесты правил, лимитов и `almatyDay`, а также интеграционные тесты HTTP-эндпоинтов.

### Допущения
- Сутки считаются по фиксированному смещению UTC+5 (Алматы), без перехода на летнее время.
- День фиксируется по `createdAt` заказа (ISO, UTC).
- Заказы с `rule: 'unassigned'` не расходуют дневной лимит филиала.
- Повторный `POST /orders/:id/assign` возвращает кэшированное распределение из в памяти `Map`, не проверяя лимит снова.

### Что бы сделал при нескольких инстансах с общей БД
- В памяти `Map` не защищает от гонки: два инстанса могут одновременно проверить лимит и оба принять заказ сверх `dailyLimit`. Нужны транзакции/`SELECT FOR UPDATE` или атомарный инкремент счётчика загрузки на (филиал, день) с уникальным ограничением, плюс уникальный индекс по `orderId` для идемпотентности повторных запросов.
