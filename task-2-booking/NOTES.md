# NOTES — задача 2. Онлайн-запись к мастеру

## Что сделано

- **Баг с пересечениями.** `overlaps` считает интервалы полуоткрытыми: запись,
  которая начинается ровно в момент окончания другой, не пересекается с ней.
- **Свободные слоты.** `getSlots` перебирает слоты с шагом 15 минут от начала
  рабочего дня и отбрасывает те, что не помещаются в рабочий день, пересекают
  перерыв или активную запись, а также начинаются не позже текущего момента.
  После каждой активной записи резервируются 7 минут на уборку.
- **Создание записи.** `POST /bookings` валидирует тело, нормализует телефон,
  проверяет мастера/услугу, переводит `start` в местное время Алматы и сверяет
  его со свободными слотами. Проверка слота и вставка выполняются под общей
  очередью, поэтому при одновременных запросах на один слот создаётся одна
  запись, второй клиент получает `409 slot_unavailable`.
- **Отмена.** `DELETE /bookings/:id` переводит запись в `cancelled`, повторная
  отмена идемпотентна (`200`), отмена менее чем за 2 часа — `409 too_late`,
  отсутствующая запись — `404`.
- **Тесты.** Ранее открытые `test.todo` закрыты в ветке `feat/slots`. В этой
  ветке добавлены собственные тесты: услуга должна целиком помещаться до конца
  рабочего дня, отменённая запись не создаёт буфер уборки, `start` принимается
  с произвольным часовым поясом, а 7-минутный буфер проверяется через API.
  Тест на одновременную бронь одного слота гарантирует ровно одну запись.

## Допущения

- Время в расписании — местное (Алматы, UTC+5), в хранилище и API — UTC.
- Отменённые записи не блокируют слоты и не создают буфер уборки.
- Буфер уборки (7 минут) добавляется после окончания активной записи и
  учитывается как занятое время при выдаче слотов.
- Значения `PORT`, `DATA_DIR`, `NOW` не меняются — по ним работают проверки.
- Хранилище остаётся в памяти, как требует задание.

## Одновременные бронирования в нескольких экземплярах с PostgreSQL

Текущая очередь (`serialize`) защищает только в пределах одного процесса. С
несколькими экземплярами приложения проверка «свободен ли слот» и вставка
должны быть атомарны на уровне БД. Варианты:

1. **Exclusion constraint (предпочтительно).** Включить `btree_gist` и запретить
   пересечение активных интервалов одного мастера прямо в схеме:

   ```sql
   CREATE EXTENSION IF NOT EXISTS btree_gist;

   ALTER TABLE bookings
     ADD CONSTRAINT bookings_no_overlap
     EXCLUDE USING gist (
       master_id WITH =,
       tstzrange(start, end + interval '7 minutes') WITH &&
     )
     WHERE (status = 'active');
   ```

   Тогда вставка/обновление, нарушающее ограничение, падает с ошибкой
   `23P01` (exclusion_violation), и приложение возвращает `409`. Буфер уборки
   входит в интервал, поэтому конфликты по нему тоже ловятся БД.

2. **Advisory lock по мастеру.** В транзакции выполнять
   `SELECT pg_advisory_xact_lock(hashtext($masterId))`, затем прочитать занятые
   интервалы, проверить слот и вставить. Блокировка снимается при коммите.
   Проще для понимания, но сериализует все операции мастера.

3. **SERIALIZABLE + retry.** Проверять слот и вставлять в транзакции уровня
   `SERIALIZABLE`, повторять её при ошибке `40001` (serialization_failure).
   Универсально, но требует аккуратного retry и не даёт декларативной гарантии.

Дополнительно:

- частичный уникальный индекс `(master_id, start) WHERE status = 'active'`
  ловит точное совпадение начала слота, но не пересечения — его стоит держать
  вместе с exclusion constraint;
- `idempotency key` в запросе на создание защищает от повторной отправки того же
  запроса при таймаутах/ретраях клиента;
- клиенту на `409` можно возвращать актуальный список свободных слотов.
